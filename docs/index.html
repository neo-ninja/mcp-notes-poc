Model Context Protocol

MCP, wired up

What MCP actually is, who talks to whom, the one place a model is involved, and what a session really means. Taught with a player, a simulator, a tool-description lab and two short quizzes.

MCP is a standard plug for functions. Any host can ask any server what do you offer?, read the schema of each tool, and call them the same way every time. Write a server once; every MCP host can use it.

model The model never talks to MCP. It reads a list of tools and, when one fits, answers with a JSON request: call this tool with these arguments. Choosing the tool and filling the arguments is the only part the model does.

host The host is the translator. It turns the model's request into an MCP call, runs it, and hands the result back for the model to read. Claude Code, Claude Desktop, Cursor and a forty-line script all play this role, and the permission prompt lives inside it.

Vocabulary

The four parties

The spec names three of them; the model is the fourth, and keeping it separate from the host is what makes the rest easy.

User

Types a sentence. Never sees JSON.

You, in a terminal or a chat window.

Host

The application. Holds the conversation, calls the model, owns one client connection per server, runs tools, asks permission.

Claude Code, Claude Desktop, Cursor, VS Code, your own script.

Model

Reads the conversation and a list of tools. Answers with text, or with a request to call a tool. Never connects to anything.

Claude, over the Messages API.

Server

A process that exposes tools, resources and prompts over JSON-RPC and runs the functions behind them.

Filesystem, GitHub, Postgres, a browser, your notes server.

Client vs host. In the spec, a client is the connection object inside the host, one per server. In conversation people say "the client" for the whole app. This guide says host for the app and client only for the per-server connection.

Building blocks

What a server offers: tools, resources, prompts

Three kinds of thing, told apart by who decides to use them.

PieceWho decidesThink of it asExamples
Toolmodel picks it mid-conversationa function with a JSON Schema for its arguments; may have side effectssearch_notes(query), create_issue(title, body), run_query(sql)
Resourcehost or user attaches itread-only data behind a URI, like a GET; no side effectsfile:///README.md, notes://groceries, db://schema/orders
Promptuser invokes ita reusable template, often with arguments; a slash command in most hosts/summarize-thread, /write-release-note version=…

In most server SDKs you write an ordinary function, decorate it, and the SDK builds the schema from the type hints and the description from the docstring. You rarely write the JSON by hand.

How a message flows

The loop

Every host runs the same loop. Nothing in it is specific to MCP except step 3, and even that is just "call a function".

  1. once, at startupConnect and ask what is on offer.

    The host opens a connection to each server (initialize), then asks tools/list. It converts each tool's name, description and schema into the format its model API expects and keeps the list.

  2. per messageSend the conversation plus the tool list to the model.

    The model replies with text (it is done) or with one or more tool_use blocks: a tool name and arguments. Nothing has run. It is a request.

  3. per tool requestThe host decides, then calls the server.

    Log it, check a policy, maybe ask the user. Then tools/call on the right server, passing the name and arguments through. The server runs the function and returns the result.

  4. then back to 2Append the result; call the model again.

    The result goes into the conversation as a tool_result. The model reads it and either asks for another tool or answers in words. The loop ends when it answers.

The single call

Where the model is called

In every host there is exactly one kind of call to the model: here is the conversation so far and here are the tools; reply. There is no separate "figure out the tool" call. The model's ordinary reply is one of two shapes:

stop_reason: "end_turn"

Text. No tool was needed, or the model has the results it asked for and is answering. The loop ends.

stop_reason: "tool_use"

One or more tool_use blocks, each with an id, a name and an input. The model chose them in the same pass where it read your message. The host runs them and calls the model again.

Because that call sits inside a loop, a task that needs two tools in sequence makes three model calls: two that request a tool, one that answers. Tools the model asks for in the same reply (parallel tool use) cost one model call between them. That loop is all an "agent loop" is.

The model decides; the host executes. The split is deliberate. Between the request and the call, the host can log, refuse, rewrite or ask the user. Every permission dialog you have seen in an MCP host lives in that gap.

Prompting

What the model is told

A host does not have to write any prompt about tools. It passes the tool definitions as a structured parameter and the model API wraps them in a hidden system prompt. Anthropic describes its shape roughly like this (the exact wording is internal and changes):

In this environment you have access to a set of tools you can use to answer the user's question.
{{ instructions for how to format a tool call }}
String and scalar parameters should be specified as is, while lists and objects should use JSON format.
Here are the functions available in JSONSchema format:
{{ the tool definitions }}
{{ the host's own system prompt, if any }}

The model was trained to follow that format: when a tool fits, it writes the call in a special syntax and the API turns it into the tool_use block. The template costs tokens on every request, which is why hosts with hundreds of MCP tools sometimes load them lazily.

The levers

Tool description

Everything the model knows about a tool. Say what it does, when to use it, when not to, and what comes back. In decorator-style SDKs this is the docstring, so the docstring is the prompt.

Argument descriptions

Each schema property can carry a description. "ISO date, e.g. 2026-11-12" prevents a whole class of wrong calls.

The host's system prompt

House rules that apply across tools: "ask before deleting", "prefer search before create". Goes after the tool definitions.

    Mechanics
    
  
    Sessions and transports
    
  
    "Is it a persistent session?" depends entirely on the transport, and the honest answer for any real system is don't rely on it.
    
  
    
    
    stdio
    The host launches the server as a child process and talks over its stdin and stdout. One handshake, then the process lives as long as the host does. One private server per host; the session is the process.
    Local tools: filesystem, git, browsers, most things you install from a registry.
    
    
    Streamable HTTP
    The server listens on a URL. Many hosts connect to one server. A session is an ID the host sends with each request; the server may track state per session, or none at all. Behind a load balancer any request can land on any instance.
    Remote and shared servers, SaaS integrations, anything with OAuth.
    
  
    
  
    Treat the connection as something that can drop, never as storage. Hosts reconnect, servers restart, a host may restart a server whenever it likes. State that matters goes in a file, a database or an external API. Keeping it in the server's memory works right up until the day it doesn't.
    

  
    
    
    Session simulator two hosts · one or two servers
    
    
    Two hosts (think: two terminal windows) use a notes server. Switch the transport and the storage, add notes from each side, search from the other, then restart things. The question each time: who can see what, and what survives.
    
    
    
      
      
      
    
    
    
    
    
    
  
    

    


    
  
    Responsibilities
    
  
    Who does what
    
  
    
    
    Model
    • Reads the conversation and the tool list
    • Decides whether a tool is needed, which one, with what arguments
    • Reads results and writes the answer
    • Never connects to anything; never knows MCP exists
    
    
    Host
    • Connects to servers; converts the tool list
    • Keeps the conversation history and resends it
    • Applies policy and permission prompts
    • Calls the server, re-wraps the result, loops
    • Lets the user attach resources and run prompts
    
    
    Server
    • Advertises tools, resources, prompts
    • Validates arguments against its schema
    • Runs the function; returns content or isError
    • Owns its own state and storage
    • May ask the host for a model answer, user input or roots

    Where the fuzz is
    
  
    What is deterministic, and what is not
    
  
    Server side, nothing is fuzzy. A tool is a function: same input, same output. You can exercise a server with no model at all:
    
  
      
    
    • MCP Inspector: a web UI that connects to any server, lists its tools, lets you fill in arguments and press call. npx @modelcontextprotocol/inspector <command to start the server>
      • 
    
    • A test client: the same SDK that hosts use, in a script, calling list_tools and call_tool directly.
      • 
    
    • By hand: type JSON-RPC lines into the server's stdin. Tedious, but it proves there is nothing hidden.
      • 
  
    
  
    The only unpredictable part is the model: whether it decides a tool is needed, which one, and what arguments it fills in. "Remember to buy eggs" becoming add_note(title="groceries", body="eggs") is that one translation. Everything upstream and downstream of it is ordinary software.
    
  
    That is why the same server works unchanged in Claude Code, Cursor, Claude Desktop and a script: the fuzzy part is on the host's side of the plug, and the plug is standard.
    

    


    
  
    Hands on
    
  
    A worked example: a notes server and a see-everything host
    
  
    Everything above was learned by building the smallest possible version: a server with two tools, one resource and one prompt, and a host of about seventy lines that prints every hop. Python, the official mcp SDK (2.x) and the anthropic SDK, in a project-local virtual environment, signed in with ant auth login rather than an API key.

    The host, client.py amber = model hops · teal = MCP hops

    """Tiny MCP client + Claude: type a sentence, watch every hop.

    you -> [LLM] -> tool_use -> [MCP server] -> tool_result -> [LLM] -> answer

Run: .venv/Scripts/python.exe client.py
Auth: `ant auth login` once (SDK picks up the profile), or set ANTHROPIC_API_KEY.
"""
import asyncio
import json
import sys

import anthropic
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

SERVER = StdioServerParameters(command=sys.executable, args=["server.py"])
MODEL = "claude-opus-5-5"


async def main():
    # 1. Launch server.py as a subprocess and do the MCP handshake (once, kept open)
    async with stdio_client(SERVER) as (read, write), ClientSession(read, write) as mcp:
        await mcp.initialize()

        # 2. Ask the server what it offers, translate to Claude's tool format
        tools = [
            {"name": t.name, "description": t.description or "", "input_schema": t.input_schema}
            for t in (await mcp.list_tools()).tools
        ]
        print(f"[mcp] server offers: {[t['name'] for t in tools]}\n")

        llm = anthropic.Anthropic()
        messages = []  # the API is stateless: we resend the whole history every call
        while True:
            try:
                text = input("you> ").strip()
            except (EOFError, KeyboardInterrupt):
                return
            if not text:
                continue
            messages.append({"role": "user", "content": text})

            while True:
                # 3. >>> THE ONLY PLACE THE LLM IS CALLED <<<
                print(f"  [llm] calling {MODEL} ...")
                resp = llm.messages.create(model=MODEL, max_tokens=16000, tools=tools, messages=messages)
                messages.append({"role": "assistant", "content": resp.content})

                for b in resp.content:
                    if b.type == "text":
                        print(f"claude> {b.text}")
                if resp.stop_reason != "tool_use":
                    break  # model is done talking

                # 4. Model asked for tools: we (not the model) execute them via MCP
                results = []
                for b in resp.content:
                    if b.type != "tool_use":
                        continue
                    print(f"  [llm wants] {b.name}({json.dumps(b.input)})")
                    r = await mcp.call_tool(b.name, b.input)
                    out = "\n".join(c.text for c in r.content if c.type == "text")
                    print(f"  [mcp returned] {out}")
                    results.append({"type": "tool_result", "tool_use_id": b.id, "content": out, "is_error": r.is_error})
                # 5. Hand results back; loop so the model can use them
                messages.append({"role": "user", "content": results})
            print()


asyncio.run(main())
    

  
    The server, server.py two tools · a resource · a prompt

    """Minimal MCP server showing the 3 primitives: tools, resources, prompts.

Run standalone check:  .venv/Scripts/python.exe server.py --check
Claude Code runs it over stdio via .mcp.json.
"""
import sys
from mcp.server import MCPServer

mcp = MCPServer("notes-poc")
notes: dict[str, str] = {}  # in-memory on purpose; a real server would use a file or sqlite


@mcp.tool()
def add_note(title: str, body: str) -> str:
    """Save a note under a title."""  # docstring = description the model sees
    notes[title] = body
    return f"Saved '{title}' ({len(notes)} notes total)"


@mcp.tool()
def search_notes(query: str) -> list[str]:
    """Return titles of notes whose title or body contains the query."""
    q = query.lower()
    return [t for t, b in notes.items() if q in t.lower() or q in b.lower()]


@mcp.resource("notes://{title}")
def read_note(title: str) -> str:
    """Read-only data the client can pull in (like a GET)."""
    return notes.get(title, f"No note named '{title}'")


@mcp.prompt()
def summarize_notes() -> str:
    """A reusable prompt template; shows up as a slash command in Claude Code."""
    return "Summarize these notes in 3 bullets:\n" + "\n".join(f"- {t}: {b}" for t, b in notes.items())


if __name__ == "__main__":
    if "--check" in sys.argv:
        import asyncio

        async def check():
            await mcp.call_tool("add_note", {"title": "mcp", "body": "Model Context Protocol"})
            print(await mcp.call_tool("search_notes", {"query": "protocol"}))
            print([t.name for t in await mcp.list_tools()])
        asyncio.run(check())
    else:
        mcp.run()  # stdio: client launches us as a subprocess and talks JSON-RPC over stdin/stdout

    Where to take it
    
  
    Next steps, in order of what they teach
    
  
    
    
    Persist the state
    Swap the dict for SQLite. Restart, search again: the session is gone, the data is not. The connection-is-not-storage rule, felt. (The simulator above shows the same thing.)
    
    
    Switch to HTTP
    Serve over Streamable HTTP and point two hosts at the same URL. Both see the same state. Then watch what a session ID does, and what happens when the server restarts.
    
    
    Wrap a real API
    Weather, a ticket board, a database. The shape stays identical; what changes is that the description now has to say when not to call it, and errors have to come back as isError text the model can act on.
    
  
    
  
    Further out: sampling (the server asks the host's model a question, reversing the arrow), elicitation (the server asks the user for input mid-call), roots (the host tells the server which folders it may touch), and OAuth for remote servers. Each is the same JSON-RPC pipe, used in another direction.
    

    


    
  
    Terms
    
  
    Glossary
    
  
    
    
    MCP
    Model Context Protocol. A JSON-RPC protocol a host uses to discover and call a server's tools, read its resources and fetch its prompts. The model is not a party to it.
    
    
    host
    The application that holds the conversation, calls the model and runs tools: Claude Code, Claude Desktop, Cursor, your script.
    
    
    client
    The connection object inside a host, one per server. Often used loosely to mean the host.
    
    
    server
    A process that exposes tools, resources and prompts and runs the functions behind them.
    
    
    tool_use
    A content block in a model's reply: a request to call a tool, with an id, name and input. A request, not an action.
    
    
    tool_result
    A content block the host sends back in the next user turn, carrying the tool's output and the tool_use_id it answers.
    
    
    stop_reason
    Why the model stopped. end_turn: it answered. tool_use: it is waiting for you to run something.
    
    
    inputSchema / input_schema
    The JSON Schema for a tool's arguments. Same thing, two spellings: camel case on the MCP wire, snake case on the Claude API.
    
    
    initialize
    The MCP handshake. Host and server agree on a protocol version and exchange capabilities, once per connection.
    
    
    stdio
    Transport where the host launches the server as a child process and talks over its stdin and stdout. One server per host; the session is the process.
    
    
    Streamable HTTP
    Transport where the server listens on a URL and many hosts connect. A session is an ID the host sends with each request.
    
    
    agent loop
    Call the model, run whatever tools it asks for, append the results, call it again, until it answers with text.
    
    
    sampling
    A server asking the host to run a model request on its behalf. The only way a server ever reaches a model, and it still goes through the host.
    
    
    roots
    Folders the host declares a server may work in.
    
    
    Inspector
    The reference web UI for poking at any MCP server by hand, no model involved.
